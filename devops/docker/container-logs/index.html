容器日志与崩溃排查

约 1245 字大约 4 分钟

2026-08-23

来源：Java 定时任务执行中服务崩溃重启（Docker 部署）相关问答整理。起点为“能否查看容器日志”一问。

一、结论

可以查看，但能看到多少、能否看到崩溃瞬间，取决于：容器是否已被 docker rm、日志是否输出到 stdout/stderr、是否配置日志轮转及是否被覆盖。

二、日志输出到 stdout/stderr（默认可见）

若应用日志（Logback/Log4j2 的 ConsoleAppender）打到 stdout/stderr，Docker 的 json-file 驱动会收集到宿主机文件，容器重启/停止后仍可用 docker logs 查看，直到容器被删除。

1. 查看当前/已停止容器日志

docker logs 容器名或容器ID
# 只看尾部 300 行（崩溃前更关心尾部）
docker logs --tail 300 容器名
# 按时间过滤
docker logs --since 1h 容器名

docker logs 默认同时输出 stdout 与 stderr。

2. 容器已停止甚至 Docker 重启后还能查吗？

只要容器未被 docker rm，日志文件仍在宿主机，默认路径：

/var/lib/docker/containers/<container_id>/<container_id>-json.log

可通过 docker ps -a 找到历史容器再 docker logs <container_id>，或直接 tail -n 500 *-json.log。

3. 关注的日志类型

  • 应用日志：定时任务执行进度、Exception/Error 栈。
  • JVM 崩溃日志：hs_err_pidXXX.log（JVM crash 时生成），不在 docker logs 中，需挂载到宿主机卷。
  • 系统层面：dmesg / /var/log/messages，容器被 OOM Killer 杀掉时宿主机可见。

三、日志写入文件而非 stdout

传统项目常写入文件如 /app/logs/app.log：

  • docker logs 通常看不到文件内容（仅抓 stdout/stderr）。
  • 若日志路径已挂载卷（如 -v /data/logs:/app/logs），直接在宿主机 tail -f /data/logs/app.log。
  • 若未挂载，只能 docker cp 容器ID:/app/logs/app.log ./ 拷出，或重启时临时挂载。

Docker 最佳实践：日志打到 stdout/stderr，由平台统一收集，而非仅写文件。

四、容器频繁重启时如何保留崩溃现场

即使重启，容器对象未删除时 json-file 仍保留日志。但以下配置会导致提前删除/覆盖：

日志轮转

json-file 默认不限大小，长期会极大；常见配置 /etc/docker/daemon.json：

{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}

含义：单文件最大 10MB，最多 3 个文件（最多 30MB）。日志量大或重启频繁时，崩溃瞬间可能被轮转掉。

避免措施：适当调大 max-size / max-file；对关键服务接入 ELK/EFK/Loki 转存到外部存储。

五、本次崩溃时间线分析

应用日志片段：

13:51:55.317 QuartzScheduler paused / shutting down
13:51:55.356 SpringContextHolder / SpringValidatorHolder destroyed
13:51:55.321 ERROR LettuceConnectionFactory is STOPPING ... leftPop
13:51:55.360 WARN DisposableBean destroy failed ... LettuceConnectionFactory has been STOPPED
13:51:55.868 DruidDataSource closing/closed
13:52:22.519 PropertySourceBeanFactoryPostProcessor Post-processing ...

解读：

  1. 正常停止阶段（13:51:55.317 - 13:51:55.886）：收到停止指令，执行优雅停机——Quartz 暂停、Spring 销毁、数据源关闭，均属正常流程。
  2. 穿插报错（13:51:55.321）：ProcessTaskSerialPostTaskPending 仍在 leftPop Redis 队列，而 Redis 连接池已先于任务关闭，属竞态条件，非崩溃原因。
  3. 间隔期（27 秒）：容器退出后编排系统（K8s/Docker Swarm）拉起新容器或 JVM 重启耗时。
  4. 重启阶段（13:52:22.519）：Spring Boot 初始化日志，新进程已启动。

结论：非 JVM Crash，是一次外部触发的正常停止 + 自动重启；LettuceConnectionFactory is STOPPING 属关闭顺序噪音。

优化：让后台任务先停再关 Redis

在持有 Redis 消费线程的 Service 中实现 DisposableBean 或 @PreDestroy：

@Component
public class ProcessTaskServiceImpl implements DisposableBean {
    private volatile boolean running = true;
    private Thread taskThread;

    public void start() {
        taskThread = new Thread(() -> {
            while (running) {
                try {
                    // leftPop 逻辑
                } catch (Exception e) {
                    if (running) e.printStackTrace();
                }
            }
        });
        taskThread.start();
    }

    @Override
    public void destroy() throws Exception {
        running = false;
        if (taskThread != null) taskThread.interrupt();
    }
}

六、dmesg 确认 OOM Kill

宿主机执行 dmesg | grep -i kill 得到：

Memory cgroup out of memory: Killed process 1530663 (java) total-vm:20635288kB, anon-rss:10460192kB ...
Memory cgroup out of memory: Killed process 284754 (java) anon-rss:10452280kB ...
Memory cgroup out of memory: Killed process 291184 (java) anon-rss:10452564kB ...
GC Thread#0 invoked oom-killer
GC Thread#2 invoked oom-killer
  • CONSTRAINT_MEMCG：Docker 容器级内存限制触发，非宿主机全局 OOM。
  • anon-rss ~10460 MB ≈ 10 GB：Java 进程死前实际占用约 10GB。
  • 三个时间点（间隔约 5-9 分钟）涉及两个容器 ID：旧容器被杀后新容器迅速又吃满 10GB 再被杀，形成“启动-吃满-被杀-重启”死循环。
  • GC Thread invoked oom-killer：JVM GC 尝试申请内存都失败，说明已无可回收空间。

七、排查步骤清单

# 1. 确认容器是否还在
docker ps -a | grep 你的服务名

# 2. 看尾部日志
docker logs --tail 500 容器ID

# 3. 看宿主机是否 OOM
dmesg | grep -i "killed process"
journalctl -k | grep -i "out of memory"

# 4. 若日志写文件
tail -f /data/logs/app.log
# 或
docker cp 容器ID:/app/logs/app.log ./

八、后续改造建议

  • 应用日志打向 stdout/stderr，至少关键级别如此。
  • 合理配置日志轮转（max-size / max-file）避免过早删除。
  • Java 服务加 -XX:+HeapDumpOnOutOfMemoryError 并挂载目录，接入日志系统。
